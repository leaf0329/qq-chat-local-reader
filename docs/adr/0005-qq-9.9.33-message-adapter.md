# ADR 0005: Strict QQ 9.9.33 message adapter

- Status: Accepted
- Date: 2026-08-30

## Context

QQ NT message tables use numeric column identifiers whose meanings are not published by Tencent. Successful SQLCipher decryption proves only that a key can open the database; it does not prove the QQ version, schema compatibility, selected account ownership, or conversation identity.

Community schema research in `QQBackup/nt_msg_db_util` documents relevant field behavior but is GPL-3.0 licensed. Its observed database facts can be independently checked, while its source expression cannot be copied or linked into this PolyForm-licensed project.

## Decision

The first adapter accepts only runtime resource version `9.9.33-52230`. It requires both `c2c_msg_table` and `group_msg_table` and verifies the declared types of the minimal columns used for identity, direction, time, display fallback, and the future message body parser. An unknown version, missing table, or incompatible column fails before any message row is returned.

The account directory name is treated only as a claimed QQ identifier. Ownership additionally requires at least one self-direction row (`40013` equal to 1 or 2) whose actual sender field `40033` exactly matches that claimed identifier in either supported message table. Failure to obtain this evidence stops the adapter instead of assuming that successful decryption implies ownership.

Conversation identity uses `40030`: private rows become private peer IDs and group rows become group IDs. Private display names use the most recent non-empty received-side `40093` value, falling back to the stable ID. Group names currently fall back to the stable ID until the separate group-information database is added. Results use ordinal ordering so GUI, CLI, and MCP consumers receive the same order regardless of locale.

The implementation is clean-room: only independently verified schema facts are used. No GPL source file, parser, or dependency is incorporated.

## Consequences

- The current QQ version and both configured local acceptance conversation types are verified without logging their identifiers or names.
- New QQ versions require a separate observed schema profile and acceptance evidence rather than optimistic reuse.
- Accounts without any locally retained self-direction message cannot yet satisfy ownership proof and fail safely.
- Rich message bodies, group names, and contact metadata remain later adapter layers; a stable conversation ID does not imply that those fields have been parsed.
